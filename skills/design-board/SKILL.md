# design-board: generate a design board from code

The board is a single SVG file holding **every screen, every state and the design rules** of the app. It is both a design
document for people and a machine-readable spec (tokens, element ids, sample data). It is generated by scripts: never
hand-drawn, never hand-edited. The style differs per app; the method does not.

> Status note (do not overstate): principles 1–3, 6 and 9 below were built and re-verified on Harness Go. Principles
> 4, 5, 7 and 8 are the stricter method that came out of building the parity check; they were proven end to end on the
> bundled example (see design-parity-flutter) but have not been back-filled into Harness Go. Start a new app with the
> strict method from day one.

## When to use

- Visual design for a new app or feature, or changes to an existing one; adding screens, states, dark mode, wide layouts.
- The user wants options compared ("show me A vs B vs C") — make a comparison board.
- Before implementation: turn the design into a form scripts can check (tokens, ids, data).

Not for: writing app code or running the parity check (→ `design-parity-flutter`).

## Core principles (each has a reason)

1. **The board is a build output.** Change the generator and rebuild; never edit the SVG. One change applies everywhere,
   and the result stays machine-checkable.
2. **One source of tokens: `tokens.json`.** Palettes (light/dark), type sizes / weights / radii / icon sizes, **named text
   styles (size + weight + line height)**, shadows, and the icon stroke rule. The board reads it; the app theme is generated
   from the same file with `gen_tokens_dart.py` — nobody copies values by hand.
3. **Scales are enforced by the tool.** Every size, weight, radius and icon size goes through `snap_*()`; off-scale input
   produces a warning and is snapped. This is what makes the design look consistent and the later per-element check possible.
4. **Every element has a stable id; every screen has a stable screen id.** `data-id="<screen>/<path>"`, e.g.
   `settings.list/row/1/title`. A screen id is a name (`settings.list`), **not** an auto number (A1, B7) — numbers shift when
   a board is inserted. In the implementation the matching id is `ValueKey('row/1/title')`. Without ids the check can only
   guess from text content or position, and a wrong guess stays silent. Mark decorative elements with `deco=True`.
5. **One copy of the sample data: `sample_data.json`.** The board and the app's preview scenes read the same file, so
   strings, item counts and order cannot drift.
6. **Measure text with the same ruler on both sides.** Estimated glyph widths put wrap points, bubble widths and baselines a
   few pixels off. Use the estimate for the first draft; before strict comparison let the **app's own text engine** measure
   (`MeasuredRuler` + Flutter's `measure_text_test.dart`, two rounds to converge) and have the board read the answers.
7. **Position text by the top of the line box.** `g.text(x, top, ..., 'body')`: style (size/weight/line height) → the baseline
   comes from measurement. With the same style in a box of the same height, the app's baseline must match. Never use
   "vertical centring + an empirical constant".
8. **Draw strokes inside the box.** `rect(stroke=...)` pushes the stroke inward (as CSS and Flutter do); SVG's default centred
   stroke otherwise makes every bordered box 1px larger than the implementation.
9. **Draw every state of every screen.** See the state matrix. A missing state gets invented by the implementer, then does
   not match the design.
10. **Decide at design time whether the implementation can draw it exactly.** Icon technique, how many stroke weights exist,
    how shadows are expressed, which font — settle these while designing and put them in the tokens. Example: Flutter icon
    fonts only have discrete weights, so the stroke rule is "pick a weight by size", not "1.8px everywhere" (the latter can
    only be met by changing the design to fit the implementation).
11. **Answer decision questions first; do not change things first.** When the user asks "A or B" or "should we add this",
    give a recommendation and the reason; if it helps to see it, make a **comparison board** (A/B/C side by side, the
    recommended one marked) and wait for the choice.
12. **Keep real data out of the sample data.** Use reserved addresses (192.168.x.x, 203.0.113.x, example.com) and example
    paths (/home/dev/…). Scan before publishing.

## Workflow (in order; each step has an exit criterion)

**0. Scope.** Establish (ask, or read from the conversation): platform and screen size, languages, brand and character,
references, required screens and flows, which states to draw. Write a paragraph in `docs/design/README.md`.
Exit: a screen list (with screen ids) and a draft state matrix.

**1. Start the project.** Copy `templates/board-kit/` into the project's `docs/design/src/`, rename the `*.example.json`
files to `tokens.json`, `icons.json`, `sample_data.json` and change their values for this app.
(`example/build_example.py` is the smallest complete example: 2 screens × light/dark.)

**2. Tokens.** Define palettes, type scale, named text styles, radii, icon sizes and stroke rule, shadows.
Exit: `python3 gen_tokens_dart.py tokens.json <out>.g.dart` runs (when the target is Flutter). **Use as few size / weight /
radius steps as possible**: every step is something that will later be checked element by element.

**3. Icons.** Pick one icon library (e.g. Lucide), write "design key → library name" in `icons.json`, and run
`python3 sync_icons.py icons.json` to fetch the official SVGs. Stroke weight is picked by size (see `reference/icons.md`).
**Use only this set.** Genuinely custom marks (brand glyphs) go under `custom`, straight segments only, so they can be built
into the icon font.

**4. Sample data.** Write `sample_data.json`: every string, item and number each screen needs. Include long copy, an over-long
title and an empty list — they trigger ellipsis, wrapping and empty states.

**5. Components → screens → rule panels.** Write components (top bar, row, button, input, bubble …) in `parts.py` using phone
coordinates (0,0 = top-left), combine them into screens in `screens_*.py` with an `id=` on every element. The rule panels
(colours, type scale, components 1:1, motion table, copy list) are boards too and go in the last section. Lay sections out
with `frame.Board` (A, B, C …): one screen per `b.screen('screen.id', 'Title', build, theme, '≤3 lines of notes')`.

**6. Build and gate.** `./build.sh`: generate → `check_board.py --require-ids` (valid XML, no `<style>`/external refs/duplicate
ids, every text and icon has an id) → `extract_layout.py` (design-side numeric JSON) → `audit_layout.py --strict` (scales,
overflow). **The version is only usable when all of these pass.**

**7. Render and look.** `render.sh board.svg out.png x y w h scale` (headless Chromium). Judge the **design itself**: spacing,
alignment, hierarchy, dark mode. (This is design review, by a person or a model looking at an image; parity is judged by
scripts only — see design-parity-flutter.)

**8. Iterate.** Feedback → change the generator → back to 6. Use comparison boards for option questions; each round say what
changed and why.

**9. Written design system.** `DESIGN.md`: principles, token table, component table (purpose, size, states), rules. The board
shows *what*; the document says *why*. When tokens change, update both (point at `tokens.json`, do not copy numbers).

**10. Publish.** Only when asked or under a standing permission; before uploading, scan for secrets and real addresses; keep
only the current version and compare the online hash with the local file.

## State matrix (walk it for every screen)

Default · empty · loading · content (short / long / over-long) · error (recoverable / not, reason shown in the UI) ·
offline / disconnected / reconnecting · disabled (buttons, inputs and icons all need one) · selected / focused / pressed ·
in progress (spinner, progress) · done · cancelled · dark · wide / landscape (if supported) · keyboard open · enlarged
system font (if supported). **Every state is its own artboard**, and the notes say which state it comes from and why.

## Rhythm with the user

- Each round: conclusion and what changed first, then links/images; list alternatives and a recommendation where there is a
  trade-off.
- **Ask** about uncertain design points instead of deciding silently; do not reopen what the user has already decided.
- Separate "verified (command + result)" from "not verified".

## Command cheat sheet (inside the board-kit directory)

```
python3 example/build_example.py --out /tmp/board.svg        # smallest example
./build.sh board.svg                                          # build + all static gates
python3 check_board.py board.svg --require-ids
python3 extract_layout.py board.svg -o build/design_layout.json
python3 audit_layout.py build/design_layout.json --tokens tokens.json --strict
./render.sh board.svg out.png 0 0 1000 2248 0.5               # render a region
python3 sync_icons.py icons.json                              # refresh icon SVGs
python3 gen_tokens_dart.py tokens.json lib/design_tokens.g.dart
```
