# design-board: generate a design board from code

The board is a single SVG file holding the screens, the composition states, the components with all their variants, and
the design rules. It is both a design document for people and a machine-readable spec (tokens, element ids, sample data). It
is generated by scripts: never hand-drawn, never hand-edited. The style differs per app; the method does not.

## When to use

- Visual design for a new app or feature, or changes to an existing one; adding screens, states, dark mode, wide layouts.
- The user wants options compared ("show me A vs B vs C") — make a comparison board.
- Before implementation: turn the design into a form scripts can check (tokens, ids, data).

Not for: writing app code, or checking that an implementation matches the board (that belongs to a dedicated
design-vs-implementation skill if one exists in the environment).

## Core principles (each has a reason)

1. **The board is a build output.** Change the generator and rebuild; never edit the SVG. One change applies everywhere,
   and the result stays machine-checkable.
2. **One source of tokens: `tokens.json`.** Palettes (light/dark), type sizes / weights / radii / icon sizes, **named text
   styles (size + weight + line height)**, shadows, and the icon stroke rule. The board reads it; every downstream
   consumer reads the same file — nobody copies values by hand.
3. **Scales are enforced by the tool.** Every size, weight, radius and icon size goes through `snap_*()`; off-scale input
   produces a warning and is snapped. This is what keeps the design consistent and the later per-element checks possible.
4. **Every element has a stable id; every screen has a stable screen id.** `data-id="<screen>/<path>"`, e.g.
   `settings.list/row/1/title`. A screen id is a name (`settings.list`), **not** an auto number (A1, B7) — numbers shift
   when a board is inserted. Without ids, no later consumer can refer to an element unambiguously. Mark decorative
   elements with `deco=True`.
5. **One copy of the sample data: `sample_data.json`.** The board and anything built from it read the same file, so
   strings, item counts and order cannot drift.
6. **Text measurement is explicit.** The default is a built-in width estimate — good for the first draft, with slack left
   for its error. If a closer measurement matters, feed `kit.init(..., measured=...)` answers produced by the target
   rendering engine (for web, a headless browser), then rebuild. Never change the sample data to dodge a wrap difference.
7. **Position text by the top of the line box.** `g.text(x, top, ..., 'body')`: the style (size/weight/line height)
   determines the baseline via the ruler. Never use "vertical centring + an empirical constant".
8. **Draw strokes inside the box.** `rect(stroke=...)` pushes the stroke inward (as CSS borders do); SVG's default centred
   stroke otherwise makes every bordered box 1px larger than intended.
9. **Draw every state, each in the layer that owns it.** See "Board form" below. A state that is drawn nowhere is a state
   the implementer will invent.
10. **Decide rendering facts while designing, and put them in the tokens.** Which font, how shadows are expressed, which
    stroke weight an icon gets at which size — settle these on the board and record them in `tokens.json` so the board is
    self-consistent and reproducible.
11. **Answer decision questions first; do not change things first.** When the user asks "A or B" or "should we add this",
    give a recommendation and the reason; if it helps to see it, make a **comparison board** (A/B/C side by side, the
    recommended one marked) and wait for the choice.
12. **Keep real data out of the sample data.** Use reserved addresses (192.168.x.x, 203.0.113.x, example.com) and example
    paths (/home/dev/…). Scan before publishing.

## Board form: screens, components, rules

The board is layered the way a designer's file is: screens carry the composition, components carry the variants, rule
panels carry the system.

| Layer | What is drawn | Strength |
|---|---|---|
| Screens | Key screens of the main flows; every state that **changes the composition** (empty, error, loading, offline, a pushed page or overlay, dark, wide/landscape, keyboard open, enlarged font) as its own artboard | Hard: a supported composition change without an artboard is unspecified |
| Components | A 1:1 component panel with **all variants** of every component — default, hover, focus, pressed, disabled, in progress — plus size steps and theme × variant cross-products | Hard: every variant must appear; variants are **not** repeated on every screen |
| Rules | Tokens, type scale, icon strokes, motion table, copy list, accessibility list | The DESIGN.md of the board |

- Fine-grained states (hover, focus, pressed, disabled) live **only** in component panels; a screen shows them through
  composition, not by duplicating the variant.
- **A state earns its own artboard only when it changes the composition** — a region appears or disappears, an overlay or
  pushed page opens, or the viewport changes (keyboard, size, theme). A state that only changes one component's
  appearance belongs in that component's panel, even across themes.
- Component states are parameters (`enabled=False`, `state='error'`); never copy a component to change one state.
- Content lengths are data, not extra screens: short / long / over-long copy lives in `sample_data.json`. One over-long
  item per list is mandatory — it is what triggers and proves ellipsis and wrapping.
- **Dark mode is another screen** (same ids, dark theme), for a small set of representative screens (usually 3–6); the
  rest of dark coverage is the theme switch drawn in the component panels.
- State matrix to walk per screen: default · empty · loading · content (short / long / over-long) · error (recoverable /
  not, reason shown in the UI) · offline / disconnected · disabled · selected / focused / pressed · in progress · done ·
  cancelled · dark · wide / landscape (if supported) · keyboard open · enlarged font (if supported). For each state, the
  notes say where it is drawn — its own artboard (composition) or the component panel (appearance) — and why; "component
  panel" is the correct answer for most of them.

## Workflow (in order; each step has an exit criterion)

**0. Scope.** Establish (ask, or read from the conversation): screen size, languages, brand and character, references,
required screens and flows, which composition states the product supports. Write a paragraph in `docs/design/README.md`
with the screen list: **every screen gets a one-line reason why it is a screen and not a component panel.** Default
budget: **≤ 40 artboards** (screens + component panels + rule panels) for a single-app board; going beyond needs a
written reason. Exit: the screen list with reasons (with screen ids), the draft state matrix, and the screen / component
split above.

**1. Start the project.** Copy `templates/board-kit/` into the project's `docs/design/src/`, rename the `*.example.json`
files to `tokens.json`, `icons.json`, `sample_data.json` and change their values for this app.
(`example/build_example.py` is the smallest complete example: 2 screens × light/dark.)
If the project already has a non-conformant generator (a custom kit, a hand-edited board), **migrate to this kit instead
of extending it**: carry over only its assets — token values, measured-text answers, icon sets — not its structure or
conventions.

**2. Tokens.** Define palettes, type scale, named text styles, radii, icon sizes, the icon stroke rule, shadows.
Exit: `tokens.json` loads in `kit.init()` and the board builds with it. **Use as few size / weight / radius steps as
possible**: every step is something the checks will later look at.

**3. Icons.** Pick one icon library (e.g. Lucide), write "design key → library name" in `icons.json`, and run
`python3 sync_icons.py icons.json` to fetch the official SVGs. Stroke weight is picked by size (see `reference/icons.md`).
**Use only this set.** Genuinely custom marks (brand glyphs) go under `custom`, straight segments only.

**4. Sample data.** Write `sample_data.json`: every string, item and number each screen needs. Include long copy, an
over-long title and an empty list — they trigger ellipsis, wrapping and empty states.

**5. Components and the pilot.** Write components (top bar, row, button, input, bubble …) in `parts.py` using phone
coordinates (0,0 = top-left). Build **one representative screen** and **one component panel**, render both PNGs, and
deliver them together with the step-0 screen list for approval **before building the rest** — this catches a wrong
direction while it costs two artboards, not the whole board. Exit: the pilot PNGs and the screen list are approved.

**6. Screens and rule panels.** Build the remaining screens from the approved list in `screens_*.py` with an `id=` on
every element. Draw the component panel with every variant. The rule panels (colours, type scale, components 1:1, motion
table, copy list) are boards too and go in the last section. Lay sections out with `frame.Board` (A, B, C …): one screen
per `b.screen('screen.id', 'Title', build, theme, '≤3 lines of notes')`.

**7. Build and gate.** `./build.sh`: generate → `check_board.py --require-ids` (valid XML, no `<style>`/external
refs/duplicate ids, every text and icon has an id) → `extract_layout.py` (numeric JSON) → `audit_layout.py --strict`
(scales, overflow) → the changed-screen list (from `screen_meta.json`, see step 8). **The version is only usable when all
gates pass.**

**8. Render and review — only the changed screens.** The generator records `build/screen_meta.json` (per screen: content
hash + render region). `render_screens.sh` renders each screen as its own PNG — or only the ones `build.sh` listed as
changed. Look at **those PNGs** and judge the design itself: spacing, alignment, hierarchy, dark mode. A whole-board
thumbnail is only for checking section order; render one when the structure changes or before the final review, not every
round.

**9. Iterate.** Feedback → change the generator → back to 7. Use comparison boards for option questions; each round say
what changed and why.

**10. Written design system.** `DESIGN.md`: principles, token table, component table (purpose, size, states), rules. The
board shows *what*; the document says *why*. When tokens change, update both (point at `tokens.json`, do not copy
numbers).

**11. Publish.** Only when asked or under a standing permission; before uploading, scan for secrets and real addresses;
render every screen once for a final pass; keep only the current version and compare the online hash with the local file.

## Rhythm with the user

- Each round: conclusion and what changed first, then links/images; list alternatives and a recommendation where there is
  a trade-off.
- **Ask** about uncertain design points instead of deciding silently; do not reopen what the user has already decided.
- Separate "verified (command + result)" from "not verified".

## Command cheat sheet (inside the board-kit directory)

```
python3 example/build_example.py --out /tmp/board.svg --meta /tmp/screen_meta.json   # smallest example
./build.sh board.svg                                            # build + all static gates + changed screens
python3 check_board.py board.svg --require-ids
python3 extract_layout.py board.svg -o build/design_layout.json
python3 audit_layout.py build/design_layout.json --tokens tokens.json --strict
./render_screens.sh board.svg build/screens [changed.txt]       # per-screen PNGs (changed only if a list is given)
python3 copy_audit.py build/design_layout.json                  # review the copy: repeats and the longest strings
./render.sh board.svg out.png 0 0 1000 2248 0.5                 # render any region (a section, a thumbnail)
python3 sync_icons.py icons.json                                # refresh icon SVGs
```
